# BUG-01 Удаление вакансии со связанным откликом

[QA-документация](README.md) · [Чек-лист](checklist.md) · [Jira ITQA-3](https://koh1o.atlassian.net/browse/ITQA-3)

**Кандидат в дефект по результатам анализа кода. Требует воспроизведения через API.** Фактический HTTP-ответ пока не получен.

## Описание

При удалении вакансии со связанным откликом ожидается нарушение внешнего ключа PostgreSQL. В сервисе удаления и обработчике ошибок не найдено преобразование этого конфликта в предусмотренную бизнес-ошибку API. Возможный результат — серверная ошибка без понятного объяснения зависимости; это гипотеза, а не зафиксированный ответ стенда.

## Предусловия

1. Приложение запущено на отдельном стенде по [инструкции](README.md#подготовка-стенда).
2. Через API созданы компания, вакансия этой компании и отклик на вакансию по [описанию тестовых данных](README.md#подготовка-тестовых-данных). Для отклика подходят `APPLIED` и корректные даты из примера.
3. Все три запроса создания вернули `201`. Из ответов сохранены `companyId`, `vacancyId`, `applicationId`.
4. `GET /api/vacancies/{vacancyId}` и `GET /api/applications/{applicationId}` вернули `200`; у отклика `vacancyId` совпадает с ID удаляемой вакансии. Ответы сохранены для сравнения.

Данные должны принадлежать только этому сценарию. В URL подставлять фактические числовые ID без фигурных скобок.

## Ожидаемый результат

**Предложение для согласования:** удаление вакансии с откликами запрещено; API возвращает `409 Conflict` в формате [ErrorResponse](../../src/main/java/io/github/koh1o/internshiptrackerapi/dto/error/ErrorResponse.java) с понятным сообщением о наличии связанных откликов. Вакансия и отклик сохраняются без изменений, технические подробности исключения не выдаются в пользовательском сообщении.

Код `409`, точный текст сообщения и политика удаления не закреплены отдельным требованием текущей версии. Сначала нужно согласовать этот контракт. Если продукт должен удалять связанные отклики каскадно, ожидаемое поведение и сценарий необходимо пересмотреть до оценки `Pass/Fail`.

## Фактический результат

**Не зафиксирован.** Запросы на работающем стенде в рамках подготовки отчёта не выполнялись. HTTP `500` рассматривается как возможный результат и требует подтверждения. Потеря данных не установлена.

## Основания гипотезы

| Источник | Наблюдение |
|---|---|
| [V1__create_initial_schema.sql](../../src/main/resources/db/migration/V1__create_initial_schema.sql) | Внешний ключ `fk_applications_vacancy` связывает `applications.vacancy_id` с `vacancies.id`; `ON DELETE CASCADE` не задан |
| [VacancyService](../../src/main/java/io/github/koh1o/internshiptrackerapi/service/VacancyService.java) | `deleteVacancy` находит вакансию и вызывает `vacancyRepository.delete(vacancy)` без проверки зависимых откликов |
| [GlobalExceptionHandler](../../src/main/java/io/github/koh1o/internshiptrackerapi/exception/GlobalExceptionHandler.java) | Нет обработчика `DataIntegrityViolationException` или специального бизнес-исключения удаления связанной вакансии |

Совместно эти наблюдения дают основание проверить необработанный конфликт целостности. Точный HTTP-код и формат ответа нельзя подтвердить только чтением этих файлов.

## Возможное влияние

Обычное действие пользователя может завершиться серверной ошибкой вместо объяснения, что у вакансии есть отклики. Сохранность записей проверяется отдельно шагами 3–4. Предварительная severity не означает, что влияние уже подтверждено.

## Проверка исправления

После согласования контракта и изменения кода:

1. Повторить сценарий удаления вакансии с откликом. Сверить код, формат и смысл ошибки с принятым контрактом.
2. При политике запрета удаления подтвердить неизменность вакансии и отклика через два `GET`.
3. Проверить, что отдельная вакансия без откликов удаляется с `204`, а последующий `GET` возвращает `404`.
4. Проверить, что удаление отсутствующей вакансии возвращает `404`.
5. Добавить интеграционную регрессионную проверку согласованного поведения в [VacancyIntegrationTest](../../src/test/java/io/github/koh1o/internshiptrackerapi/integration/VacancyIntegrationTest.java). Существующий `shouldDeleteVacancy` проверяет удаление вакансии без откликов.

После сохранения доказательств очистить тестовые данные в порядке «отклик → вакансия → компания», как описано в [QA README](README.md#очистка).
